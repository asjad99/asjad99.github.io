<p>Data is tricky to manage once the operations scale. It can grow exponentially, coming in from new sources, and becoming more diverse, which makes it increasingly challenging to process and find insights. Mature organizations like Google, Airbnb and Uber have a well-established data culture. Some of the lessons we can draw from such mature organizations, in terms of establishing best practice are as follows:</p><ul><li>Data should be treated as code. i.e, creation, deprecation, and critical changes to data artifacts should go through the review process with appropriate written documents where stakeholder's views are taken into account.</li><li>Each data artifact should have a clear owner, and a clear purpose and should be deprecated when its utility is over.</li><li>Data artifacts have tests associated with them and are continuously tested.</li><li>Considering the full end-to-end flow of data across people and systems — can lead to higher overall data quality.</li><li>Teams should aim to be staffed as <em>full-stack</em>' so the necessary data engineering talent is available to take a long view of the data’s whole life cycle. While there are complicated datasets that can be owned by more central teams, most teams that produce data should aim toward local ownership.</li></ul><p>Let's Consider Machine Learning as our primary use-case for building the data platform. Following are some of the key stages for implementing an ML based solution:</p>

<p>Once the initial protoyping and experiments are completed we need to </p><p><em>Enterprise grade ML,</em> a term mentioned in a paper put forth by Microsoft, refers to ML applications where there is a high level of scrutiny for data handling, model fairness, user privacy, and debuggability. While toy problems that data scientists solve on laptops using a CSV dataset could be intellectually challenging, they are not enterprise-grade machine-learning problems.</p><p>Deploying ML models requires major manual oversight. We need to ensure:</p><ul><li>Models have been optimized with the right balance between complexity and accuracy. </li><li>Data Pipelines are robust with the required level of monitoring. </li><li> The right level of data and concept drift monitoring is implemented for model re-training. </li><li>In deployment (via containers or spark applications, for example), governance becomes paramount, especially in regulated environments. The data preprocessing begins with data transformation and cleaning tasks. The data engineer/scientist defines the data transformation rules (normalization, aggregations) and cleaning rules to bring the data into a usable format. i.e The transformation rule artifact defined in the requirement gathering stage serves as input for this task. These transformation rules are continuously improved based on feedback. Workflow orchestration coordinates the tasks of an ML workflow pipeline according to directed acyclic graphs (DAGs).</p><p><strong>Model Registry: </strong>The model registry stores centrally the trained ML models together with their metadata. It has two main functionalities: storing the ML artifact and storing the ML metadata</p><p><strong>MLFlow Tracking: </strong>The development of a workflow happens through many iterations. Multiple variants of the project may be tested concurrently, developed by a team of data scientists working simultaneously. Metadata is tracked and logged for each orchestrated ML workflow task. Metadata tracking and logging is required for each training job iteration (e.g., training date and time, duration, etc.), including the model-specific metadata—e.g., used parameters and the resulting performance metrics, model lineage: data and code used—to ensure the full traceability of experiment runs. Data Scientist will build models and log them to MLflow, which records environment info. “ML assets” as ML model, its parameters and hyperparameters, training scripts, training and testing data. We aim at recording the the identity, components, versioning, and dependencies of these ML artifacts.</p><p><strong>CI/CD pipeline automation.</strong> Data Scientists move models to Staging where we introduce a CI/CD system to perform fast and reliable ML model deployments in production. The core difference from the previous experimental step is that we now automatically build, test, and deploy the ML Model, and the ML training pipeline components.</p><p><strong>Model Serving:</strong> The model serving component can be configured for different purposes. Examples are online inference for real-time predictions or batch inference for predictions using large volumes of input data. The serving can be provided, e.g., via a REST API. As a foundational infrastructure layer, a scalable and distributed model serving infrastructure is recommended. Will likely require Azure kubernetes service. </p><p><strong>Monitoring: </strong>The monitoring component takes care of the continuous monitoring of the model serving performance (e.g., prediction accuracy). Models may degrade over time. We check for concept drift and whenever performance degrades, new data is available, the process of model retraining is triggered. This level of automation also includes data and model validation steps.</p><p></p><hr><p><strong>References and Further reading</strong></p><ul><li>MLOPS: <a href="https://outerbounds.com/docs/infra-stack" rel="noopener noreferrer">https://outerbounds.com/docs/infra-stack</a><br> <a href="https://ml-ops.org/content/mlops-principles" rel="noopener noreferrer">https://ml-ops.org/content/mlops-principles</a><br> <a href="https://arxiv.org/pdf/2205.02302.pdf" rel="noopener noreferrer">https://arxiv.org/pdf/2205.02302.pdf</a><br>-<a href="https://www.youtube.com/watch?v=tuIR1Jz2P8k&amp;ab_channel=Databricks" rel="noopener noreferrer">https://www.youtube.com/watch?v=tuIR1Jz2P8k&amp;ab_channel=Databricks</a> </li><li>Building a Data Integration Team: Skills, Requirements, and Solutions for Designing Integrations</li><li>30-day error rates for data-related issues in Google's TFX model serving system [Breck et al., SysML 2019]</li><li>Hidden Technical Debt in Machine Learning Systems</li><li>Harnessing Organizational Knowledge for Machine Learning</li><li>The Chief data Management officer handbook</li></ul>
